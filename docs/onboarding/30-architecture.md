## The request lifecycle

A request hits the application via the OpenShift Route (TLS termination) and lands at the adapter-node HTTP server. Then:

```
HTTP request
   ↓
[adapter-node] — parses up to BODY_SIZE_LIMIT bytes; rejects 413 if larger
   ↓
hooks.server.ts: handle = sequence(
   ↓
   handlePhase1
     - maybeStartOcrWorker (first request only)
     - maybeStartChefsPoller (first request only)
     - maybeStartSearch (first request only — starts the search reconciler)
     - assigns requestId (nanoid 12)
     - issues cydb_csrf cookie if absent
     - applies rate limit on POST / (legacy; route is archived)
     - attaches child logger to event.locals.logger
   ↓
   handleBetterAuth
     - reads session cookie
     - if valid, populates event.locals.user + event.locals.session
     - runs better-auth's own internal routes (/api/auth/*) here
   ↓
   handlePopulateRoles
     - if event.locals.user: loads roles from userRoles table
     - else if NODE_ENV !== production AND DEV_AUTH_BYPASS set:
         parses bypass config, finds ?bypass=email or cookie or first persona,
         calls applyBypass → seeds user, sets event.locals.user + .roles,
         emits 'auth_bypass_applied' audit event
   ↓
   handleRoleGuard
     - matches event.url.pathname against ROUTE_RULES
     - if rule matches AND no user: redirect 303 → /login?next=...
     - if rule matches AND wrong role: audit 'role_denied', throw 403
     - else: let the request continue
   ↓
   handleSecurityHeaders (wraps the inner resolve)
     - calls resolve(event) to render the page / hit the endpoint
     - applies X-Frame-Options, CSP, nosniff, Referrer-Policy,
       HSTS (prod), Cache-Control (staff routes only) to the response
   ↓
)
   ↓
Response back to adapter-node → Route → client
```

`event.locals` is a per-request typed object. Its shape is declared in `src/app.d.ts`:

```ts
interface Locals {
  requestId: string;
  user?: { id: string; email: string; name: string };
  session?: Session;
  roles: Set<Role>;
  csrfToken: string;
  logger: Logger;
}
```

## ROUTE_RULES (the role-gate table)

In `src/hooks.server.ts`:

```ts
const ROUTE_RULES: Array<{ prefix: string; roles: Role[] }> = [
  { prefix: '/admin',       roles: ['admin'] },
  { prefix: '/clinician',   roles: ['clinician'] },
  { prefix: '/submissions', roles: ['admin', 'cfd_worker'] },
  { prefix: '/attachments', roles: ['admin', 'cfd_worker', 'clinician'] }
];
```

Match algorithm: `path === r.prefix || path.startsWith(r.prefix + '/')`. So `/admin` matches the admin rule; `/admin/queues` also matches; `/admin../foo` doesn't (and isn't a real route anyway).

If the path doesn't match any rule, the request passes through ungated. **Public routes are public by default — adding a route to a role-gated area requires no extra wiring, but adding a *new* role-gated prefix means adding a row to ROUTE_RULES.**

`/attachments/[id]` is double-gated: the route rule allows all three roles in, then the endpoint joins to `submissions` and runs `canAccessAttachmentByStatus(roles, status)` to enforce a per-status policy. See `50-auth-and-roles.md` for the matrix.

## In-process workers

Three workers run in the same Node process as the HTTP server. They start lazily on the first request that reaches `handlePhase1`. Once started, they tick on their own `setInterval` until process shutdown.

### OCR worker

Started by `maybeStartOcrWorker()` in `hooks.server.ts` when `env.OCR_WORKER_ENABLED === '1'`. It calls `startWorker({…})` in `src/lib/server/ocr/worker.ts`, which returns a `WorkerHandle` (`stop()` for graceful shutdown).

Each tick:
1. **Check halt sentinel.** `getSystemState(db, 'ocr.halted')` — if set, skip everything.
2. **Lease a job.** `acquireLease(db, now)` — transactional UPDATE that picks the oldest `status=queued` job whose `nextAttemptAt` has passed, marks it `status=leased`, returns it.
3. **Process the job.** `processJob(...)` — read the attachment file, call the configured OCR provider, store the result in `ocr_analyses`, run the keyword evaluator (`keywords.ts`), update `submissions.status` to `OCR processed` (or `OCR Error`).
4. **On failure:** `recordFailure(...)` — increments per-job `attempts`, sets `nextAttemptAt` with back-off, transitions to `OCR Error` after `OCR_MAX_ATTEMPTS`.
5. **Breaker.** If consecutive terminal failures cross `OCR_FAILURE_BREAKER`, write `ocr.halted` to `system_state`, send an alert email via `selectMailer(...)`, stop dispatching.

The breaker can only be cleared by an admin through `/admin/queues` or `/admin/ocr` (or manually clearing `system_state` rows for debugging).

### CHEFS poller

Started by `maybeStartChefsPoller()` when the effective CHEFS config has `pollerEnabled=true`. Calls `startPoller({…})` in `src/lib/server/chefs/poller.ts`.

Each tick:
1. **Check halt sentinel** (`chefs.halted`).
2. **`listSubmissions(...)`** against the CHEFS export API to get new submission IDs since the last sync.
3. **For each new submission:** `runIngest(...)` — fetch the submission JSON, map to our schema (`mapper.ts`), `downloadAndPersist(...)` the file references, `writeValidSubmission(...)` to insert the row + attachment rows, `enqueueAttachmentForOcr(...)` for each file.
4. **On consecutive failures:** breaker writes `chefs.halted` + sends the alert mail.

The single-flight pattern (no overlapping ticks) is handled by an in-memory flag in the poller closure.

### Search reconciler

Started by `maybeStartSearch()` in `hooks.server.ts`. Calls `startReconciler({…})` in `src/lib/server/search/reconciler.ts`. This is the third in-process background loop.

Each tick: `selectDirty(db)` finds rows where `submissions.search_indexed_at IS NULL OR search_indexed_at < updated_at`, then calls `indexSubmission(...)` for each, which writes to the Manticore index over HTTP. Covers new submissions, CHEFS ingests, status changes, and any push that was missed.

## Search (Manticore)

Full-text search on `/submissions` is backed by a **Manticore Search sidecar container** (`manticoresearch/manticore:25.0.0`) running in the same Pod as the app. It is reached over `localhost:9308` using plain HTTP JSON DSL (`/search`) and `/sql` — no Kubernetes Service or Route; it is never reachable from outside the Pod. See `80-deployment.md` for the Pod spec and sidecar configuration.

### Request / hydrate / re-auth flow

```
Browser: GET /submissions?q=smith&status=pending
   ↓
submissions loader (+page.server.ts)
   ↓ requireRole('admin', 'cfd_worker')         ← auth check first
   ↓ status filter applied to scope the corpus
   ↓
runSearch(query.ts)
   ↓
ManticoreClient.search(manticore.ts) — HTTP POST localhost:9308/search
   returns: [ { id, relevance, snippet }, … ]   (BM25-ranked)
   ↓
loader re-fetches full rows from SQLite by those IDs, preserving hit order
   ↓ status filter re-applied against SQLite                  ← second auth boundary
   ↓ canAccessAttachmentByStatus / requireRole already enforced above
   ↓
Page rendered with ranked, highlighted results
```

**SQLite is the source of truth; the authorisation boundary stays in the DB.** Manticore returns only IDs; the loader re-runs the same status filter against SQLite before rendering. Search cannot widen access.

### What's in the index

Each submission is indexed as a single Manticore document in the `submissions_idx` index, with four text fields:

| Field | Content |
|---|---|
| `structured_text` | Form fields expanded to human labels via `OPTIONS` (e.g. `"Autism Spectrum Disorder"` not `"ASD"`) |
| `ocr_text` | Raw text extracted by OCR from attachments |
| `metadata_text` | Request metadata (IP, UA, timestamp) |
| `surname` | Applicant surname for exact-prefix matching |

Index settings: `morphology=lemmatize_en_all`, `min_infix_len=2`, `index_exact_words=1`. Fuzzy matching is on by default. The document is built by `buildSearchDocument` in `document.ts`, which calls `OPTIONS` label-expansion at index time so the index content matches what staff read in the UI.

### Freshness: real-time push + reconciler

`submissions.search_indexed_at` is a nullable timestamp column that acts as a dirty marker.

- **Real-time push**: when an OCR job completes, `process-job.ts` calls `onIndexed` (after the DB transaction commits, best-effort) to index the updated row immediately.
- **Reconciler**: the background loop (described above) catches anything the push missed — new submissions, CHEFS ingests, status changes, process restarts.

A row is considered dirty when `search_indexed_at IS NULL OR search_indexed_at < updated_at`.

### Health

`/readyz` includes a `search` probe (`pingSearch` from `search/health.ts`) that issues a lightweight request to Manticore. Manticore down → `/readyz` returns 503, blocking traffic from the Route until it recovers. This means a failed sidecar is immediately visible in the readiness gate — it will not silently serve stale or empty search results.

## Single-flight pattern

Both the OCR worker and CHEFS poller — and the OAuth2 token caches (CHES, Kong) — use the same idiom for deduplicating concurrent work:

```ts
let inflight: Promise<T> | null = null;
async function getThing() {
  if (cachedAndFresh()) return cached;
  if (inflight) return inflight;            // ← share the in-flight promise
  inflight = doExpensiveThing().finally(() => { inflight = null; });
  return inflight;
}
```

If you find yourself doing the same thing in new code, follow this pattern. The unit tests for `ChesTokenCache` cover the dedup case so the contract is locked in.

## Halt sentinel pattern

State that survives across process restarts goes in the `system_state` key/value table. The OCR and CHEFS halts use this. Pattern:

```ts
// To halt:
setSystemState(db, 'ocr.halted', { trippedAt, threshold, lastErrorClass });

// To check at runtime:
if (getSystemState(db, 'ocr.halted')) return;  // skip this tick

// To clear (admin action only):
clearSystemState(db, 'ocr.halted');
```

The value can be any JSON; you don't need to define a new column.

## Static + signing

- **Static assets** are bundled by Vite and served by adapter-node from `build/client/`. No CDN.
- **The pino logger** writes JSON-per-line to stdout. OpenShift's log aggregator picks it up. There's no app-side rotation or fanout.
- **OAuth state cookies** for the SSO flow are signed by better-auth using `BETTER_AUTH_SECRET`. PKCE is enabled so even with a stolen authorization code the attacker can't trade it for a token.

## What's coupled, what's not

- `db` is a global; every module imports `{ db } from '$lib/server/db'`. Pure functions (`lease`, `process-job`, `mapper`) all accept the db as a parameter — that's deliberate, it lets unit tests pass in an in-memory SQLite.
- The mailer + OCR provider + keywords list are passed into `startWorker(...)` as constructor args, not imported globally. Same for the CHEFS client (`list` + `download` callbacks). That's the seam tests use.
- `event.locals.logger` is the request-scoped child logger; workers use the top-level `logger` from `$lib/server/log` instead. Both go through the same PII redactor.
- Form schemas (`zod` definitions in `src/lib/form/schema.ts`) are built from the Form.io JSON at module load. Don't hand-maintain enums in TypeScript — they would drift from the deployed CHEFS form.
